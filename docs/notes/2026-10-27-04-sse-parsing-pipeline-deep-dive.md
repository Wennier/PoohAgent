# 深挖：浏览器里手写 SSE + AG-UI 事件解析管线

- 批次：Day 1
- 卡片类型：**技术深挖卡**（面试主讲这张；`01-sse-frame-splitting` 是它的踩坑实例）
- 产出代码：`src/transport/sse-parser.ts`、`src/transport/event-parser.ts`、`src/transport/agent-gateway.ts`
- 产出测试：`test/split-frames.spec.ts`、`test/parse-sse-frames.spec.ts`、`test/parse-frame.spec.ts`

## 一、为什么必须自己写，不能用现成的

| 方案 | 为什么不行 |
| --- | --- |
| `EventSource` | ① 只能 GET，带不了 `messages` 请求体；② 不能自定义 header（真实环境要带 XSRF）；③ 只能 `close()`，区分不了"用户取消"与"网络断开" |
| `@microsoft/fetch-event-source` | 可用，但把「重连策略/重试次数」也包进去了，与我们要的「由业务层用 cursor 续流」冲突 |
| `eventsource-parser` | 帧解析可用；但事件语义层（坏帧隔离、未知 type 透传）仍要自己写 |
| `@ag-ui/core` 的 `HttpAgent` | 现网曾用它，实测其内部管道引入额外事件延迟，才改成手写 fetch —— **这是一个可讲的性能决策** |

结论：**帧解析可以复用库，但事件语义层必须自控**。我们选择两层都自己写，是为了让每一层都能独立单测。

## 二、管线分层（一张图讲完）

```
HTTP 响应
  │  ReadableStream<Uint8Array>      任意边界，可能在 UTF-8 字符中间切开
  ▼
[1] 字节 → 字符    TextDecoder({ stream: true })
  │  字符串缓冲（保留不完整字符）
  ▼
[2] 字符 → 帧      splitFrames(buffer) → { frames, rest }
  │  按空行切分；剥 data: 前缀；多行 data 用 \n join
  ▼
[3] 帧 → 事件      parseFrame(frame) → AgentEvent | null
  │  JSON.parse + 形状校验；失败返回 null（不抛）
  ▼
[4] 事件 → 消息     （Day 2 的归约层，不在本卡范围）
```

**分层判据**：每一层的"出错单位"不同——[1] 错在字符、[2] 错在帧边界、[3] 错在 JSON。分开之后，出问题能立刻定位到层，而不是在一个 200 行的大函数里猜。

## 三、细节清单（这一节才是面试的主菜）

### [1] 字节 → 字符

| # | 细节 | 踩错的后果 |
| --- | --- | --- |
| 1 | `TextDecoder` 必须 `{ stream: true }` | 中文被切片时变成 `�`，且**偶发**（取决于 TCP 在哪切） |
| 2 | 流结束时 `decoder.decode()` 的**返回值要拼回缓冲区** | 丢掉最后半个字符；且返回值常被误当成"刷新动作"而丢弃 |
| 3 | 不能对每个 chunk 单独 `new TextDecoder().decode(chunk)` | 同上，必现乱码 |
| 4 | 流的 `Uint8Array` 可能是 `ArrayBufferView` 的任意切片 | 直接 `buf.toString()` 会按 UTF-16 解，得到乱码 |

### [2] 字符 → 帧（SSE 规范相关）

| # | 细节 | 说明 |
| --- | --- | --- |
| 5 | 帧分隔是**空行**，不是 `\n\n` 这个"两个字符" | 语义是"一个空行结束一帧"；行尾可能是 `\r\n` / `\n` / **单独的 `\r`** |
| 6 | 归一化顺序：先 `\r\n → \n`，再 `\r → \n` | 反了会把 `\r\n` 变成 `\n\n`，凭空多出空段，`rest` 计算错位（**我自己踩过**） |
| 7 | 一帧可含多行 `data:`，值用 `\n` join | 不是直接拼接，否则 JSON 少了换行符 |
| 8 | `data:` 后跟一个**可选空格**，规范要求去掉一个 | `data:{...}` 与 `data: {...}` 都合法 |
| 9 | 以 `:` 开头是注释行；`event:` / `id:` / `retry:` 是其他字段 | 我们只处理 `data`，其余忽略；心跳常用注释行 |
| 10 | 分派条件：data 缓冲非空 | 纯注释块不应产生事件 |
| 11 | 缓冲区必须保留**残片**（`rest`），一个字节都不能丢 | 丢了表现是"偶尔少一个字"，极难复现 |
| 12 | 最后一段在"流未结束"时只是**可能不完整** → 只能进 rest，不能进 frames | 混进去会产生残帧 + 重复（**我自己踩过**） |
| 13 | 流结束时规则反转：残留即完整 | 用 `splitFrames(buffer + '\n\n')` 再切一次取尾帧 |
| 14 | 开头可能有 BOM | 规范要求忽略；否则首个 `data:` 行匹配不上 |

### [3] 帧 → 事件

| # | 细节 | 说明 |
| --- | --- | --- |
| 15 | 解析失败**返回 null 而不抛** | 一帧坏不能毁掉整条流；代价是错误被静默吞掉（见 01 卡的踩坑） |
| 16 | 非对象 / 缺 `type` 也返回 null | `"abc"`、`123`、`[1,2]`、`null` 都要挡掉 |
| 17 | **未知 type 必须透传** | 否则 Day 3 接 `TOOL_CALL_*` 时会"莫名收不到事件" |
| 18 | 事件**顺序必须保持** | 同一 `messageId` 的 CONTENT 靠顺序累积；一旦做并发处理就会乱序 |

## 四、五个设计取舍（面试可主动抛）

1. **纯函数 + 生成器的组合**
   `splitFrames` 是纯函数（可单测五种切法），`parseSseFrames` 只负责读流 + 解码 + 拼接。如果把两者揉在一起，测试就必须伪造 `ReadableStream`——成本高一个数量级。

2. **坏帧跳过 vs 整条流失败**
   选跳过：流式场景下"部分可用"比"全有全无"体验好。但必须让失败**可观测**（`console.warn` + 计数），否则会重演 01 卡那次"一个事件都收不到还不报错"。

3. **不实现 `Last-Event-ID` / `retry` 自动重连**
   SSE 规范提供 `id` + `retry` 做断线续传。我们不做，因为后端已经给了 `display_state` + `next_cursor`（`/history` + `/readstream`），**续传语义归业务层**更可控。这是一个"协议能力 vs 业务能力"的边界判断。

4. **性能：避免每 chunk 全量 `split`**
   当前实现每个 chunk 都对整个 buffer 做一次 `split('\n\n')`。若帧很大、chunk 很小，会退化成 O(n²) 重复扫描。更稳的写法是用 `indexOf` 定位分隔符、只切一次并推进游标。目前消息量级小，先留注释不改——**知道边界在哪，比提前优化重要**。

5. **取消（AbortSignal）要穿透三层**
   `signal` 必须传给 `fetch`；`reader.read()` 会抛 `AbortError`；上层要能区分"用户取消"与"网络失败"。任何一层漏传，都会表现为"点了中止但请求还在跑"。

## 五、追问（准备这些就够了）

- 如果后端从 SSE 换成 WebSocket，这套分层哪几层要重写、哪几层能复用？
- 如果一帧有 10MB，你的缓冲策略要怎么改？`buffer += chunk` 在 V8 里真的会 O(n²) 吗？
- 60+ 条 CONTENT 事件如果并发处理，怎么保证不乱序、不丢？
- 每帧都触发一次 React `setState` 会卡，节流应该做在解析层还是归约层？（Day 2/3 的真实问题）
- 断线重连后如何做到"不重复渲染已有消息"？（幂等 / 游标 / 消息 id 去重）
- 为什么"解析失败返回 null"比"抛错"更符合流式场景？代价是什么、怎么补偿？
