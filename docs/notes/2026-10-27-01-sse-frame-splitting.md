# SSE 帧解析：把字节流切成事件

- 批次：Day 1
- 模块：A1 协议接入 / `src/transport/sse-parser.ts`
- 涉及测试：`test/split-frames.spec.ts`、`test/parse-sse-frames.spec.ts`（共 16 条用例）

## 现象

`splitFrames` 单测 7 条挂 6 条，`parseSseFrames` 9 条全挂。更早的端到端现象是：
mock 服务端日志显示发出了 70 条事件，但客户端**一个事件都收不到**，且没有任何报错。

我实测自己的实现，输入：

```
data: {"type":"A"}\n\ndata: {"type":"B"}\n\ndata: {"type":"C"
```

输出：

```
frames: ["data: {\"type\":\"A\"}", "data: {\"type\":\"B\"}", "data: {\"type\":\"C\""]
rest  : "data: {\"type\":\"C\""
```

三个问题同时在：帧里带着 `data: ` 前缀、最后那段不完整的帧被当成了完整帧、`rest` 和 `frames` 里出现了同一段内容。

## 根因

四条独立的原因叠在一起：

1. **只过滤、没剥前缀**。用 `startsWith('data: ')` 挑出了帧，但没把 `data: ` 去掉，下游 `JSON.parse('data: {...}')` 必然失败。而 `parseFrame` 的设计是「解析失败返回 null，不抛错」，于是失败被静默吞掉——表现就是"什么都没收到"，而不是报错。
2. **"最后一段进 rest" 的规则被用反了**。这条规则的前提是"流还没结束，后面还会有字节"，所以最后一段不确定是否完整。但它同时又被 `filter` 挑进了 `frames`，导致残帧被当成完整帧产出。
3. **按"段"处理而不是按"行"处理**。SSE 的 `data:` 可能有多行（多行 payload 要用 `\n` join），一个段里也可能混着注释行（以 `:` 开头）、`event:`、`id:` 行。只判断整段是否以 `data: ` 开头，这些情况全错。
4. **`\r\n` 与 `\n` 两种行尾**。HTTP 规范允许 `\r\n\r\n`，某些代理/实现还会发畸形的孤立 `\r`。

## 方案

- 先把行尾统一：`\r\n → \n`，再处理孤立的 `\r`。**顺序不能反**——反过来会把 `\r\n` 变成 `\n\n`，凭空多出空段，导致 `rest` 计算错位。
- 切分后的**最后一段只作 `rest`**，从前 N-1 段里取完整帧（`segments.slice(0, -1)`）。
- 每段**按行处理**：挑出以 `data:` 开头的行 → 去掉 `data:` 与紧随的一个空格 → 用 `\n` 连接。
- 流结束时**再切一次**：此时"残留"已经不可能再有字节补充，就是完整内容，用 `splitFrames(buffer + '\n\n')` 就能把它当作"前面的一段"切出来。

- 为什么 SSE 用「空行分隔」而不像二进制协议那样用长度前缀？各自对粘包/拆包的处理成本是什么？

- `parseFrame` 选择"解析失败返回 null 而不抛错"，这个决策的代价是什么？（答案的一部分就在本次现象里：错误被静默吞掉）
- 一个 chunk 里可能出现两帧、半帧、甚至半帧的第一行被切开——这三种情况分别由哪一层负责处理？
