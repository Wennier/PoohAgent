## 〇、协作约定（**最高优先级，冲突时以此为准；开工前必读**）

### A. 写入权限

1. **默认只给改法，不动文件**。任何写入动作（改源码、改 `package.json`、新增/删除文件、装依赖、跑 `pnpm install`、写文档）都必须先问一句"要我改吗"，得到明确同意后才执行。
2. **只做点名的那一处**。就算"不改就编译不过"，也只**报告**：哪个文件、哪一行、为什么挡路、最小修法是什么，等指令。
3. **每轮结尾列出本轮改动文件清单**，方便核对是否越界。
4. 发现别处有问题，只报告，不顺手修。

### B. 功能实现流程（**每个新功能都必须按这个顺序**）

1. **自上而下实现**：先定"用户看到什么"（产品场景与目标效果），再定数据契约（类型与字段），最后才写实现。**禁止先堆底层零件再往上拼**——零件先落地会导致没有调用方、无法验证。
2. **先复现**：动手前先在页面（或最小脚本）上复现"现在的现象"——不对的表现、缺失的能力、报错或空白。复现不出来就不动手：那说明还没搞清要解决什么。
3. **一步一步实现**：每步只动一层/一处，做完立刻验证（页面现象 + `pnpm typecheck` + `pnpm test`），通过后再进下一步。每步结束时说明"现在这一步改了什么、下一步是什么"。

> 判定标准：如果一轮里有 3 个以上文件被改、且中途没有一次页面级验证，说明"一步一步"没做到。

## 一、项目定位与约束

### 1.1 为什么重写

准备 agent 开发岗位面试。现网对话能力已在主干投入使用，但主要实现者不是本人。通过从零实现一遍，达到两个目的：

1. 真正吃透一条完整的 agent 会话链路（协议 → 归约 → 状态机 → 渲染 → 会话管理 → HITL）；
2. 沉淀可讲述的问题卡片：**遇到的问题、误判、根因、方案与权衡**。

因此**面试价值是排序的第一权重**，不是功能完整度。

### 1.2 硬约束

| 维度 | 结论 |
| --- | --- |
| 周期 | 1 周，每天 5 小时，共约 35 小时 |
| 节奏 | **硬节奏**：一天一批，当天验收通过才进下一批；时间不够就砍尾部批次 |
| 端 | 仅 PC Web，不为 MP / Electron 预留抽象 |
| 协议 | 必须对接现网 agentgateway（AG-UI 事件流），协议不可改 |
| 落位 | **仓库根目录**（本仓库即该包），现网五包保持不动，可随时对照 |
| 依赖 | 不依赖 `@tencent/docs-ai-*` 任何内部包；外部通用库（React / rxjs / markdown 渲染器）允许 |

### 1.3 已知取舍（面试时可主动讲）

| 不做 | 原因 |
| --- | --- |
| 应用外壳（assistant / home、页面路由、标题栏） | 面试价值低，纯产品壳 |
| 产物右侧预览、产物列表页 | 依赖 preview-kit 与宿主能力，成本高收益低 |
| 积分商业化、赞踩反馈 UI | 与后端计费强耦合；只保留数据通道 |
| 语音输入 | 复用现成能力即可，自研无增量价值 |
| Slate 富文本编辑器 | 编辑器内核不是 agent 议题；用 textarea + chip 模型替代 |
| 文件上云上传（import-kit） | 依赖外部服务，改做图片 base64 与文档引用 |
| 长列表虚拟化 | 性能优化项，一周内不是瓶颈（消息量级小） |
| Plugin 扩展机制 | 无第二方接入需求；设计思路写进笔记即可 |

## 二、产品视角模块拆解

按「一个对话产品要交付什么能力」切分，共 **7 个域 / 24 个模块**。每个模块给出：职责、必须实现的能力点、必须处理的异常路径、明确不做的部分。

> 异常路径是本文最重要的部分——它们是面试验证「你是否真的写过」的地方。

### 域 A｜消息通道与协议（4 个模块）

#### A1 协议接入（SSE 客户端）

- **职责**：向 `POST /api/v6/agentgateway/chat` 发起流式请求，把 SSE 字节流还原为有序事件序列。
- **必须实现**
  - 请求体构造：`thread_id`（新会话为空串）、`messages`（全量历史，wire 格式）、`contexts[0].{channel, params}`
  - 从 `RUN_STARTED.threadId` 回填会话 ID
  - SSE 帧解析：`data:` 多行拼接、帧间空行分隔、UTF-8 跨 chunk 截断
  - 中止：`AbortController` 断开 + `POST /cancel` 通知后端
- **异常路径**
  - HTTP 非 200 / 登录失效（业务码 439902）→ 不进归约层，直接进错误层
  - 流中途断开（网络抖动）→ 与「正常结束」必须可区分
  - abort 与「服务端刚好发 RUN_FINISHED」竞态 → 不得重复收尾、不得把状态拉回 Generating
  - 心跳/空帧 → 忽略且不计入事件
- **不做**：自动重连（重连策略归 B3 的 restore）

#### A2 事件归约引擎

- **职责**：事件序列 → 消息列表。这是整个项目的技术核心。
- **必须实现**
  - **双通道**
    - 直播通道：chunk 增量（`TEXT_MESSAGE_CONTENT` / `REASONING_MESSAGE_CONTENT` / `TOOL_CALL_ARGS`）按 id 追加
    - 快照通道：`MESSAGES_SNAPSHOT` 全量重建（走聚合器，不复用增量逻辑）
  - 工具结果配对：`TOOL_CALL_RESULT` 按 `toolCallId` 回填到所属 assistant 消息的 tool part
  - 自定义事件扩展：`CUSTOM{name}` 责任链，未知 name 静默跳过
- **异常路径**
  - delta 重复投递 → 同 id 重复内容不得翻倍（或明确接受并记录）
  - END 事件先于 START；`TOOL_CALL_RESULT` 先于 `TOOL_CALL_END`
  - 未知事件类型 / 未知 CUSTOM name → 跳过且不污染消息
  - 快照与直播同时到达 → 以快照为界重建，之后的增量才追加
- **不做**：事件持久化、回放

#### A3 消息模型（领域模型）

- **职责**：定义 UI 层真正消费的数据结构，是渲染层与归约层之间的契约。
- **必须实现**
  - `UIMessage { id, role: 'user' | 'assistant', parts: Part[] }`，user 与 assistant 同构
  - `Part` 判别联合：`text` / `reasoning` / `tool` / `image` / `online_doc` / `selection` / `reminder` / `error` / `artifacts` / `credits`
  - 协议消息（扁平 role 列表）与 UI 消息（聚合后按轮次）的**双向映射职责清晰**：上层只认 UI 消息
  - assistant 占位机制：提交时先插入空 assistant 消息，首个 `TEXT_MESSAGE_START` 时接管其 id
- **异常路径**
  - 历史消息缺 id → 生成稳定本地 id
  - 同一逻辑消息被拆成多条（多段文本）→ 聚合规则需明确
  - `reminder` 属于隐藏上下文 → 不得出现在可见文本中
- **不做**：消息持久化（交给后端）

#### A4 会话快照与历史

- **职责**：把后端历史接口的响应转成可渲染的消息列表，并判定是否还有活体任务。
- **必须实现**
  - `POST /history` → `{ messages, display_state, next_cursor }`
  - wire 消息反序列化（`content_parts` / `tool_calls` / `content`）
  - `display_state ∈ {in_progress, needs_input}` → 标记需要续接实时流
- **异常路径**：历史为空、`next_cursor` 为空串（走无 cursor 模式）、历史消息含未知 role（`custom`、`activity`）

### 域 B｜对话会话（5 个模块）

#### B1 会话状态机

- **职责**：定义「什么时候可以做什么」，是所有交互门禁的唯一来源。
- **必须实现**
  - 三态：`Ready` / `Generating` / `Restoring`
  - 门禁：Generating / Restoring 期间拒绝新提交；Restoring 期间拒绝发送与中止
  - abort：断开流 → 追加「用户已取消」错误 part → 回到 Ready；abort 请求未返回前不得被旧流事件拉回 Generating
- **异常路径**
  - abort 进行中收到旧流事件
  - 连续两次 abort
  - restore 失败后重试（必须先清空旧消息，否则脏数据混入）
- **不做**：暂停/续跑（HITL 走 F2）

#### B2 发送编排

- **职责**：把「一次用户输入」变成一次合规的协议请求。
- **必须实现**
  - parts → 协议内容编译：文本编入 text part；`selection` / `image` 以 XML payload 编码；`local_file` / `online_doc` / `template` 走独立 content part；`reminder` 单独成段
  - 派生 `hiddenContext`（如 XML 语义提示）
  - 入队 user 消息 + 插入 assistant 占位
  - 状态切 Generating，取出事件流交给 A2 消费
- **异常路径**：parts 为空（不可发送）、编译后可见文本为空但附件非空（可发送）、提交时状态已变
- **不做**：输入框读取（那是域 D 的责任）

#### B3 历史恢复

- **职责**：打开已有会话时，把历史与「可能仍在跑的任务」一次性接上。
- **必须实现**
  - history 快照 → 渲染完整历史
  - `display_state` 判定：仍在跑 → 先跑完整快照，再以 `cursor` 续接 `readstream`，并切到 Generating
  - 恢复完成后的定位：指定 messageId 则滚动到该消息，否则滚到底部
- **异常路径**
  - 恢复期间用户又切换会话（旧请求必须作废）
  - 历史已齐但实时流无事件（空跑）
  - 恢复失败（网络/无权限）→ 空态 + 可重试
- **不做**：离线缓存

#### B4 重新生成

- **职责**：对某条 assistant 回复重新跑一轮，而不产生新的 user 消息。
- **必须实现**
  - 由 assistant messageId 反查其所属 user message
  - 从该 user 消息的结构化内容恢复 parts 与 hiddenContext
  - 以「新的一轮」重新提交（历史保留，末尾追加）
- **异常路径**：找不到源 user 消息、生成中/恢复中调用、重生成后原回复的处理（覆盖 or 追加需明确）
- **不做**：多版本回复切换

#### B5 运行错误与重试

- **职责**：把四类错误变成用户能理解的一句话，并决定是否可重试。
- **必须实现**
  - 错误来源分类：`query`（请求未建立）/ `stream`（流中断）/ `run`（服务端 RUN_ERROR）/ `tool`（本地工具执行失败）
  - 错误作为 `error` part 追加到当前 assistant 消息，而不是独立状态
  - 业务码 → 文案映射（439902 未登录、439903 无权限、439906 限流、439907 积分不足…）
  - 可重试标记，与 UI 的「重试」按钮联动
- **异常路径**：错误发生在尚无 assistant 消息时（需先建空 assistant）、连续多次错误、重试导致消息重复
- **不做**：错误上报服务（只留接口）

### 域 C｜消息呈现（7 个模块）

#### C1 渲染管线

- **职责**：`Part` → React 组件的映射与扩展点。
- **必须实现**
  - part 级渲染器注册表（按 `part.type` 分发）
  - 消息级渲染器（user 气泡 / assistant 容器）
  - 未知 part 类型的兜底（渲染为空并告警，不崩溃）
  - 中间件机制：外部可优先接管某类 part（产物卡片、积分卡片用得上）
- **不做**：Slot/Menu 体系

#### C2 富文本段落渲染

- **职责**：把流式到达的 Markdown 稳定渲染出来。
- **必须实现**
  - Markdown 渲染 + 代码块高亮 + 外链
  - **流式未闭合修复**：代码围栏、行内代码、加粗在流式中途都是未闭合的
  - 增量渲染的性能控制（节流/仅在帧内渲染一次）
- **异常路径**：每帧全量重解析导致卡顿、超长代码块、HTML 注入（必须禁用 raw HTML）
- **不做**：公式、图表、自定义指令

#### C3 推理过程展示

- **职责**：展示模型思考过程，不干扰正文阅读。
- **必须实现**：折叠区、流式更新、结束后保持可展开；与正文的视觉层级区分
- **异常路径**：推理与正文交错到达（顺序必须保持）、推理为空

#### C4 工具调用可视化

- **职责**：让用户看到「模型在干什么」——这是 agent 产品与聊天机器人的分水岭。
- **必须实现**
  - 参数流式累积（分片 JSON **不可**逐片 `JSON.parse`，只能累积后解析）
  - 状态机：调用中 → 执行中 → 成功 / 失败
  - 结果回填与折叠展示
  - 与正文的穿插顺序正确
- **异常路径**：参数 JSON 不合法、结果缺失（流断）、同一 toolCallId 重复、结果早于结束事件
- **不做**：工具自定义渲染协议（只做通用卡片）

#### C5 消息操作

- **职责**：用户对已有内容能做什么。
- **必须实现**：复制（区分纯文本/带 Markdown）、重新生成（接 B4）、错误重试（接 B5）
- **不做**：分享、导出文档、赞踩

#### C6 空态

- **职责**：没有消息时给用户一个开始的方式。
- **必须实现**：欢迎语 + 推荐问（可直接触发发送）
- **不做**：服务端推荐接口（用静态配置）

#### C7 滚动与跟随

- **职责**：流式输出时视图要跟着走，但用户上滑时必须让位。
- **必须实现**
  - 粘底（stick to bottom）：流式新增内容时自动跟随
  - 用户上滑 → 取消粘底 → 出现「回到底部」按钮
  - 历史恢复期**抑制**自动贴底，避免回放时视图乱跳
  - 指定消息定位（点击历史消息跳转）
- **异常路径**：图片异步加载导致高度突变、恢复完成与定位的时序竞争、平滑滚动与即时贴底冲突
- **不做**：虚拟列表

### 域 D｜输入与提交内容（3 个模块）

#### D1 输入区与发送门禁

- **职责**：接收用户输入，并判断此刻能不能发。
- **必须实现**
  - 多行文本输入、Enter 发送 / Shift+Enter 换行
  - 门禁：内容为空不可发；Generating / Restoring 不可发（按钮态 + 提示）
  - 发送后清空输入
- **异常路径**：中文输入法组合态下按 Enter（不得误发）、发送瞬间状态变化
- **不做**：Slate 富文本、@ 提及、模板插槽

#### D2 内容片段组装

- **职责**：把输入区的内容转成 `AgentSubmitPart[]`（本项目的核心契约之一）。
- **必须实现**
  - 文本 + 图片 + 在线文档引用 + 选区 → 有序 parts
  - 去重（同一 fileId / 同一图片不重复插入）
  - 空内容判定（只有附件也算非空）
  - 隐藏上下文（reminder）不进入可见文本
- **异常路径**：parts 顺序错乱导致模型理解偏差、只有空白字符、附件删除后仍被提交
- **不做**：文件上云、本地路径投递（Web 无此能力）

#### D3 附件 chip 管理

- **职责**：待发内容的可视化与增删。
- **必须实现**：chip 展示（图标 + 名称）、删除、图片预览
- **异常路径**：同一文档重复添加、上传中占位（本项目用本地 URL，无需上云）

### 域 E｜会话管理（4 个模块）

#### E1 会话列表

- **职责**：让用户看到并管理所有会话。
- **必须实现**
  - `POST /runtimes` 拉列表（分页 50）
  - 首屏刷新 + 触底加载更多，in-flight 去重
  - 删除会话（本地 + 远端）
- **异常路径**：加载失败、列表为空、删除当前活动会话
- **不做**：重命名、置顶（余力再加，各约 20 行）

#### E2 活动会话与状态隔离

- **职责**：保证「一个会话一份状态」，切换时不串数据。
- **必须实现**
  - 每个会话持有独立的消息列表、状态机、输入草稿
  - 切换会话 = 切换被消费的会话实例
  - 切换时不销毁已加载会话（懒创建 + 缓存）
- **异常路径**：切换时旧会话仍在流式输出、切回已删除会话
- **不做**：多 Tab 同步

#### E3 草稿会话提升

- **职责**：新建会话在发送第一条消息前不应产生空会话记录。
- **必须实现**
  - 草稿只存在本地，标题为「未命名」
  - 首条消息拿到真实 `threadId` 后提升为正式会话
  - **提升顺序必须保证任意中间态都能解析出活动会话**（先入列表 → 再切 activeId → 最后清草稿）
  - 首轮结束后回填服务端生成的标题
- **异常路径**：提升瞬间的状态竞争导致「发送后回到初始态」、草稿重复创建
- **不做**：多草稿

#### E4 恢复上次会话

- **职责**：刷新页面后回到上次的会话。
- **必须实现**：`localStorage` 记录 activeId（含草稿标记）；启动时恢复，跨页加载直到命中；失效则回退首项
- **异常路径**：记录的会话已被删除 / 无权限、记录损坏

### 域 F｜HITL 与工具交互（2 个模块）

#### F1 本地工具注册与执行

- **职责**：让服务端可以在流中「点名」前端执行一个工具。
- **必须实现**
  - 工具注册表（name → handler）
  - 流内工具：`TOOL_CALL_END` 后立即执行，执行期间流保持等待（`isInStream`）
  - 工具执行上下文：`toolCallId`、`interruptId`
  - 中间件：可在执行前后插入逻辑（埋点、权限校验）
- **异常路径**：工具未注册、参数不合法、执行抛错（不得中断整条流）
- **不做**：回合末批量工具 + interrupt resume（现网有实现但主流程未接线，本项目按「已知取舍」记录）

#### F2 AskUserQuestion 问答交互

- **职责**：模型向用户提问，用户作答后继续同一轮对话。
- **必须实现**
  - 卡片形态：单选 / 多选 / 自定义输入
  - 问答进行中**接管输入区**（用户不能自由输入）
  - 答案以 `role: 'tool'` 消息 + `answer_token` 回传原 `/chat` 接口，续接同一流
  - 卡片状态：待答 → 提交中 → 已答
- **异常路径**：无 threadId 时提交、重复提交、提交失败回滚、提问被新提问覆盖（旧 promise 必须 reject）
- **不做**：多步表单、历史问答回看交互

### 域 G｜工程支撑（3 个模块）

#### G1 极简容器

- **职责**：解决「同一份能力在多个会话实例间隔离」的问题。
- **必须实现**：`register / resolve / 惰性实例化 / 生命周期释放 / React Context 桥`
- **不做**：父子容器、resolveAll、singleton、装饰器注入

#### G2 状态与事件

- **职责**：渲染层订阅数据的方式统一。
- **必须实现**：`Observable` 风格的 store（含当前值的 Subject）、组件订阅 hook、事件总线
- **不做**：全局状态管理库

#### G3 demo 载体

- **职责**：一个能跑起来的验证页面（左侧会话列表 + 右侧对话区）。
- **必要**：一周内所有验收都在它上面完成。

## 四、六个批次（硬节奏）

每批结束必须有一个**能看见的产物**并通过验收清单，否则不进入下一批。

### Day 1｜协议打通

- **模块**：G1、G2、A1（最小）
- **今日目标**：点发送 → 真实请求 → 控制台按序打印每一个 SSE 事件（类型 + 主要字段）
- **完成定义**：能连续发 3 次不同内容都不崩；中止按钮能断开连接
- **验收清单**
  - [ ] 请求体字段与协议文档一致（`thread_id` / `messages` / `contexts`）
  - [ ] 能从 `RUN_STARTED` 拿到并保存 threadId
  - [ ] 打印的事件顺序与协议文档「典型事件序列」一致
  - [ ] 点中止后连接确实断开，且 `/cancel` 被调用
- **预期踩坑**：SSE 帧被 TCP 切半、`data:` 多行拼接、XSRF/凭证、`content-type` 不匹配导致流不被识别

### Day 2｜归约与最小渲染

- **模块**：A2、A3、C1、C2（最小）、B1
- **今日目标**：发送后出现 user 气泡，assistant 文本逐字流式输出，结束后回到 Ready
- **完成定义**：一轮完整对话可跑通；中止可用；刷新前不崩
- **验收清单**
  - [ ] user 消息与 assistant 占位顺序正确，占位 id 被服务端 id 接管
  - [ ] 文本按 delta 追加，无重复、无丢失
  - [ ] 中止后状态回到 Ready，且旧流不再改写消息
  - [ ] RUN_ERROR 能显示为用户可见的错误文案
- **预期踩坑**：占位 id 替换时机、END 无 START、快照与增量混用、abort 竞态

### Day 3｜推理与工具

- **模块**：C3、C4、F1
- **今日目标**：推理折叠区 + 工具调用卡片（参数流式、执行中、结果）
- **完成定义**：能完整展示「推理 → 调工具 → 二次正文」这一标准序列
- **验收清单**
  - [ ] 参数分片累积后一次性解析，不逐片 parse
  - [ ] 工具卡状态与实际事件一致
  - [ ] 工具结果正确回填到所属 assistant 消息
  - [ ] 推理与正文的先后顺序不乱
- **预期踩坑**：`TOOL_CALL_RESULT` 先于 `TOOL_CALL_END`、结果消息与调用消息分属不同 role 需配对、参数非 JSON

### Day 4｜输入与消息操作

- **模块**：D1、D2、D3、C5、C6、C7
- **今日目标**：可发送「文本 + 图片 + 文档引用」的多段消息；空态、复制、重生成、滚动跟随可用
- **完成定义**：手写一条带 2 个附件的消息，模型能正确理解；流式时视图跟随、上滑不打断
- **验收清单**
  - [ ] parts 顺序稳定，图片/文档引用编码符合协议

  - [ ] 中文输入法 Enter 不误发

### Day 5｜多会话与恢复

- **今日目标**：问答卡片可交互并续流；断网/中断有提示与重试；README 与笔记成集

### Day 5 之后｜**已排期**：消息内分区（过程 / 结论分离）

> 状态：已排期（不属于 Day 1~6 的硬节奏范围）。触发原因：Day 4 做消息操作时发现，现在一条消息里的 parts 是平铺的，没有「过程折叠 + 结论单列」的产品效果。

**产品效果**（对齐 Claude Code / Cursor）：

```
⌃ 已完成 · 用时 33 秒              ← 折叠条（过程）
   ⌃ 执行了命令
   ⬡ 思考 · …（推理内容）
   >_ 运行命令 · webSearch
我先用 webSearch 查一下…            ← 正文（结论）
北京今天晴，气温 28°C。
```

**判据（不需要协议改动）**

- 完成态：`status === Ready` 且该消息不再增长 → `completed = true`
- `completed === true`：找**最后一个 `text` / `error` part**，它之前的全部收进折叠组，之后的直接可见
- `completed === false`（流式中）：**不折叠**，只把「连续的 tool / reasoning」收拢成一组，且**最后一项保持可见**
- 折叠组内部再按"连续 process part"分组，避免每个工具卡各占一层

这套判据来自现网 `workspace-kit/src/chatbox/feature/message-list/common/resolve-groups.ts`（`resolveGroups`），已验证可用。

**前置条件（必须先做）**

1. **`reasoning` part 未实现** —— 折叠组里目前只有工具卡，"思考"这项永远缺失，效果不完整。需先补：
   - `ReasoningPart`（`message/type.ts`）
   - `REASONING_*` 事件分支（`ui-transform.ts`）
   - 快照侧 `role: 'reasoning'` 合并（`aggregateSnapshot`，Day 3 决策 D3：并入相邻 assistant，作为第一个 part）
   - mock 增 `?scenario=reasoning`
2. 完成态信号已有，无需改协议

**落位**

- 纯函数：`src/message/resolve-groups.ts`（`ResolvedGroup = CollapseGroup | Part`，可单测）
- 组件：`src/render/process-group.tsx`（折叠条 + 子项）
- `demo/main.tsx` 的 `MessageBubble` 改为遍历 `resolveGroups(...)` 的结果

**工作量**：约半天（分组纯函数 2h + 组件与样式 1.5h + 测试 0.5h）

**代价与边界（要写进注释）**

- 启发式的固有误差：模型若"先给结论、再调工具补充"，会把结论折进过程。现网也接受这个误差，因为 agent 范式通常是"先做后说"
- 流式中折叠收起最后一项，会让用户看不到正在执行的工具 —— 所以"最后一项保持可见"是硬要求

**协议层的升级路径（暂不做）**

现网 `agent-kit` 已定义 `role: 'activity'` + `activityType` 与 `ACTIVITY_SNAPSHOT` / `ACTIVITY_DELTA` 事件，说明协议允许后端下发**带类型的活动项**（如"执行了命令"）。若后端开始真正下发 `activity`，可把启发式换成按类型分组。当前后端（我们 mock 与现网）都没用它，所以先用启发式。

## 五、五个技术攻坚点（面试主战场）

| # | 攻坚点 | 一句话讲法 |
| --- | --- | --- |
| 1 | 双通道归约 | 直播走增量、快照走全量重建，两条路径共用同一个 UI 模型——直播时不能依赖历史，回溯时不能依赖增量 |
| 2 | 状态机与 abort 竞态 | abort 是一个「主动收尾」过程：先断流、再收状态、最后才允许下一次提交，否则旧流会把状态拉回去 |
| 3 | 历史与实时衔接 | 历史接口返回 `display_state` + `cursor`，据此决定「只渲染历史」还是「渲染历史后接上仍在跑的流」 |
| 4 | 草稿提升的原子性 | 三个状态不是原子更新的，中间态必须可被解析，否则用户看到的是「发送后回到初始页」 |
| 5 | 流式渲染与滚动让位 | 流式时内容高度持续变化，滚动策略必须是「粘底 + 用户意图优先 + 恢复期抑制」 |

## 六、问题卡片机制

目录：`docs/notes/`，文件名 `YYYY-MM-DD-序号-简述.md`。

```md
## 现象
（错误信息 / 异常表现 / 错误数据，原样保留）

## 误判
（我一开始以为是什么——这段最有价值）

## 根因
（实际是什么，为什么）

## 方案
（怎么修的；放弃了哪些备选方案，为什么）

## 追问
（面试官继续问时，还能深挖什么）
```

规则：
1. **当场记**，不要事后补；只记「卡住超过 20 分钟」的问题。
2. 每天收尾花 15 分钟整理卡片，不足一张就说明当天太顺，需要主动往深挖。
3. 每批结束把当批卡片链接汇总到 `docs/notes/README.md`。
