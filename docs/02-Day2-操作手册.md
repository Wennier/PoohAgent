## M1 能看见自己的消息（30 min）

**改哪里**：`src/agent/agent-controller.ts` 的 `submit()`

**只实现前 4 步，先不订阅流**：

1. 状态门禁：`status === Generating` → `return false`
2. 文本 trim 后为空 → `return false`
3. `store.push({ id, role: 'user', parts: [{ type: 'text', content: text }] })`
4. `store.push(createAssistantPlaceholder())`
5. `status$.next(Generating)`

**页面验收**：点发送 →

## M2 能看见回复逐字长出来（60 min）

这一步是 Day 2 的主体，分三小步做，每步都能在页面上看到进展。

### M2.1 `MessageStore.replaceId`（10 min）

**为什么需要**：提交时插的占位消息 id 是本地生成的 `assistant_xxx`，后端第一个 `TEXT_MESSAGE_START` 才带来真实 `messageId`。要把占位"接管"成真实 id，**且消息数不能变**。

**三条边界**（测试里都有）：
- 命中 → 替换并返回 `true`
- 未命中 → 返回 `false`，不抛错
- 目标 id 已存在 → 不能变成两条（重复 START 会走到这里）

**验收**：`pnpm test` 里 `message-store` 变成 12/14。

### M2.2 `applyLiveEvent` 的 START / CONTENT（40 min）

**START 分支**：取最后一条消息 —

```
最后一条是 assistant 占位 → store.replaceId(占位id, event.messageId)
已存在同 messageId        → 直接 return（重复事件）
否则                      → push 新 assistant 消息
```

**CONTENT 分支**：`store.appendText(event.messageId, event.delta)`，注意 `delta` 可能是空串。

**页面验收**：点发送 → 助手气泡里的文字**逐字增长**，右侧日志同时打出 60+ 条 `TEXT_MESSAGE_CONTENT`。

**两个坑**：
- 如果你发现文字不是追加而是每次覆盖，检查 `appendText` 是不是"替换"而不是"拼接"
- 如果发现出现两条 assistant 气泡，检查 START 分支有没有做"已存在则 return"

### M2.3 订阅流（10 min）

补上 `submit()` 剩下的那步：

```
connect({ threadId, messages: buildWireHistory(), channel: 'doc', signal })
  .subscribe({
    next:     onEvent?.(event); applyLiveEvent(store, event);
              event.type === 'RUN_STARTED' && threadId$.next(event.threadId)
    error:    收尾（M4 细做）
    complete: status$ = Ready; abortController = null
  })
```

**页面验收**：一轮完整跑通，顶部 `status` 从 `generating` 回到 `ready`。

## M3 能看见错误挂在回答末尾（30 min）

**改两个地方**：

1. `MessageStore.appendPart` — 命中就追加；**未命中要新建一条 assistant 消息承载它**（"请求还没开始就失败"是最常见边界）
2. `applyLiveEvent` 的 `RUN_ERROR` 分支 — 拼 `ErrorPart`，挂到最后一条 assistant 消息上；没有 assistant 就用占位新建

**页面验收**：把 mock 的响应改成中途报错（临时在 `buildScript` 里加一条 `{ type: 'RUN_ERROR', message: '模型超时' }`），页面应显示"半截文本 + 红色错误"，而不是整个气泡消失。

**测试**：`message-store` 14/14、`ui-transform` 里 RUN_ERROR 那两条通过。

## M4 能中止（20 min）

**改哪里**：`AgentController.abort()`

三行逻辑，但有一个关键约束：

```
没有在途 controller → 直接 return（不报错）
否则 → abortController.abort()
```

**收尾不要在 `abort()` 里做**——交给 `subscribe` 的 `error` 回调统一处理，否则会和 error 回调**重复执行**（状态被置两次、错误 part 被追加两次）。

同时把 `error` 回调写完整：

```
AbortError（DOMException，name === 'AbortError'）→ 追加「用户已取消」error part
其他错误                                        → 追加 error.message
两种情况都要：status$ = Ready、abortController = null
```

**页面验收**：
- 生成中点「中止」→ 日志出现 `✕ 已中止`，**不是红色报错**
- 顶部状态回到 `ready`
- 「发送」按钮恢复可点

## M5 历史快照重建（30 min）

**改哪里**：`ui-transform.ts` 的 `aggregateSnapshot`（纯函数，不影响页面，最后做）

规则：
- `role` 为 `user` / `assistant` → 各生成一条 UIMessage
- 其他 role（`tool` / `reasoning` / `custom`）→ **跳过**（Day 3 再合并回父消息）
- 缺 `id` → 生成 `local_${index}`，不能留空
- `content_parts` 里的 text 优先于 `content`（后端约定，`extractWireText` 已给好）

**关键测试**是最后那条 **「直播与快照产出一致」**：同一段对话，直播拼出来的文本必须等于快照重建出来的文本。这条过了，说明两条路径没有走偏。

## 附：实现顺序为什么是这样

```
M1 submit（落消息）        ← 页面先能看到"我发的"
      ↓
M2 replaceId/appendText/START/CONTENT  ← 页面能看到"它在回"
      ↓
M3 appendPart/RUN_ERROR    ← 出错时页面不崩
      ↓
M4 abort                   ← 能打断
      ↓
M5 aggregateSnapshot       ← 纯函数，不阻塞前面任何一步
```

每一步都有**页面上能看见的产物**。如果某一步做完页面没变化，说明线没接对——先查 `useAgent` 的订阅，而不是怀疑业务逻辑。
