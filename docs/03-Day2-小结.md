## 一、双通道归约：是什么，重点在哪

### 词拆开看

**"通道"** = 数据进入系统的路径。同一个会话，数据有**两种完全不同的形态**进来：

| | 直播通道 | 快照通道 |
| --- | --- | --- |
| 触发 | 用户刚发消息，等回复 | 打开已有会话 / 刷新页面 |
| 数据形态 | **一条条事件**：`TEXT_MESSAGE_CONTENT{delta:"你"}` | **一整个数组**：`[{role:'assistant', content:'你好世界'}]` |
| 只能怎么做 | **增量**：往已有消息上追加 | **全量**：直接重建 |
| 实现 | `applyLiveEvent(store, event)` | `aggregateSnapshot(wireMessages)` |

**"归约"**（reduce）是函数式术语：把一串东西折叠成一个结果。直播通道是把**事件序列**折叠成消息；快照通道是把**协议消息数组**映射成 UI 消息。

所以"双通道归约" = **两条入口，一个出口**：两条路径最终都产出同一种 `UIMessage[]`。

### 为什么这算"重点"而不是"顺手实现一下"

**只做直播通道**：打开历史会话时手里没有任何事件，只有一份消息数组——只能**伪造一串事件**去重放。而真实历史与事件流对不上：历史里 `assistant` 只有 `content` 没有 `TEXT_MESSAGE_START`，`tool` 结果是独立一条消息（直播里是 patch 回父消息），还可能缺 id。用增量逻辑重放历史，会得到"刷新后消息结构变了"。

**只做快照通道**：用户发完消息要等整轮结束才看到内容——逐字输出就没了。

**两条都做，才是最难的**：两份实现必须产出**结构完全一致**的结果，否则会出现「刚发的消息（走直播）和刷新后的同一条消息（走快照）长得不一样」。为此有一条测试专门守这个不变量：

```
同一段对话，直播拼出来的文本 === 快照重建出来的文本
```

### 一句话

> 双通道归约的本质不是"写两个函数"，而是**给消息构造定义了一条不变量**：两条路径必须收敛到同一个规范形式。难点全在"不变量怎么定义、怎么守住"。

### 比图更重要的两样东西

**① 每层"不知道什么"**

架构不是画方块，是画**认知边界**。上面每层的 `✗ 不知道` 才是真正的内容：

- transport 不知道消息——它只认字节和帧
- 归约不知道状态——它只认事件和消息
- store 不知道 React——它只推数据
- controller 不知道 UI——它只切状态
- React 不知道协议——它只渲染

任何一条被打破，就会出现"改协议要动 UI"这类耦合。

**② 三条不变量**（规定模块之间的契约，比模块清单重要）

1. **两条路径等价**：`aggregateSnapshot(协议消息) ≡ 直播事件折叠的结果`
2. **一端一个状态源**：`status$` 只由 controller 写，归约层与视图层只读
3. **store 只进不可变快照**：任何更新都产出新数组/新对象，不原地改

## 三、技术难点：诚实的评估

先给结论：**Day 2 这一段本身没有系统级难点**。它是数据变换 + 状态机，规模小、边界清晰。硬凑三五条"深度"只会一追问就露馅。

上一版总结列了 5 条，只有第 4 条够格；其余是"实现说明"——"选了 B 而不是 A"不叫取舍，叫记录。以下是重评后的结果。

### 够格的难点 1：`finish` 混了两种生命周期（已修）

- **问题**：`RUN_ERROR` 一到就调用 `finish()`，它顺手把 `abortController` 置为 null。
- **后果**：此时流其实还开着，但用户再点中止时 `abort()` 因 `!this.abortController` 直接 early return → **中止静默失效**，请求继续跑完。
- **本质**：把「run 的生命周期」误当成「连接的生命周期」。正确做法是拆成两件事 — `settleRun()`（只改状态）与 `releaseConnection()`（释放 controller / subscription）。
- **为什么值得讲**：单测全绿时这个 bug 依然存在，只有真实链路实测才能发现。这类"建模错误 + 测试盲区"的组合，是工程判断力的直接证据。
- **实测证据**：`RUN_ERROR` 在流中途到达后点中止，文本仍从 38 字涨到 168 字（全文），`parts` 为 `[error, text(全文)]`。

### 够格的难点 2：规范形式（canonical form）与归约的等价性 —— **我们没解决，只是埋下了**

- **表层说法**："两条路径要一致"。深下去：一致指什么？文本相等？结构相等？还是"可观察行为"等价？
- 一旦引入工具调用，等价性会**退化**：直播路径产出一条 assistant 消息里 `[text, tool, text]`；快照路径后端给的是**三条扁平消息** `assistant(tool_calls)` + `tool(result)` + `assistant(text)`。折叠时你必须回答：
  - tool 结果挂到父消息的**哪个位置**？（tool_calls 的位置，还是结果到达的位置？）
  - 并行多个 tool call，顺序按什么定？
  - 后端**没给** `parentMessageId`，只能靠"最近一个带 tool_calls 的 assistant"去猜——猜错怎么办？
- 真正的深度是：**协议本身有歧义时如何定义归约的规范形式**；规范形式不可完全确定时，用启发式还是推动改协议。
- 状态：**Day 3 就会撞上**，目前未处理。

### 够格的难点 3：逐帧不可变更新的代价 —— **我们完全没做优化**

- 现状：每收到一条 `delta`，产出**新数组 + 新消息对象 + 新 parts**，`BehaviorSubject` 推全量快照。
- 两层代价：
  - **复制成本**：每条消息一次 O(n) 数组复制，一轮 60 帧 → O(n·frames)
  - **渲染成本**：每次 next 都可能触发整棵树重渲染
- 解法分层，每层都有代价：
  - 只替换变更那条（结构共享）→ 仍要复制数组
  - 按消息粒度订阅 → store 要放弃"全量快照"语义，改增量事件 + selector
  - rAF / throttle 合帧 → **直接增加端到端延迟**，"逐字"变"一跳一跳"
- 真正的取舍是 **端到端延迟 vs 每秒渲染次数**，需要选一个 frame budget。现网 workspace-kit 的选择是 rAF 节流 + `useHasMessage(throttleMs)`（专为避免"仅最后一条内容变化"触发重渲染），那是经验值，不是推导出的最优解。
- 面试口径：讲"知道代价在哪、什么时候付账"，**不能讲"我解决了"**。
