## 步 1｜空态推荐问题（15 min）

### 产品问题

**P1**：新用户打开是一片空白，不知道能问什么 → 首轮流失。

### 改哪里

只改 `demo/main.tsx`。

### 做法

1. 常量 `SUGGESTIONS`（3~4 条静态问题，先不接后端）
2. `EmptyTip` 接收两个 prop：`disabled`（生成中禁用）、`onPick(text)`
3. **空态由 `App` 决定，不由 `MessageList` 决定**：

```tsx
{messages.length === 0
  ? <EmptyTip disabled={isStreaming} onPick={text => submit(text)} />
  : <MessageList messages={messages} />}
```

为什么不让 `MessageList` 内部判断：空态是"没有消息时的页面状态"，属于场景层。`MessageList` 一旦接收 `onPick`，它就开始知道业务了。

### 验收

- 空态显示 4 条推荐问题，点击后**直接发出**（不经过输入框）
- 生成中按钮禁用（连点不会发两条）
- 发出后空态消失、出现用户气泡

### 顺带验证的一条路径

点推荐问题走的是 `submit(text)` → 与输入框回车同一条链路，但**不经过 Composer**。这条路径能验证"提交与输入框解耦"是否真的成立。

## 步 2｜消息复制（20 min）

### 产品问题

**P2**：AI 的回答无法取用 —— 用户只能手动选中、拖拽、复制，长回答体验很差。

### 改哪里

`demo/main.tsx` 的 `MessageBubble`（先做助手消息，用户消息同理可加）。

### 做法

1. 底部加一行操作区：`复制`
2. 复制内容 = 该消息所有 `text` part 拼接（用 `getTextContent`）
3. 用 `navigator.clipboard.writeText`；失败（非 https / 无权限）时 fallback 到提示

```tsx
const copyable = getTextContent(message);
if (!copyable) return null;   // 没有文本就不要显示按钮
```

### 验收

- 助手消息底部出现「复制」，点击后粘贴得到纯文本（不含工具卡）
- 工具卡消息（没有文本）不显示复制按钮
- 复制成功有轻提示（复用日志区或 Snackbar 都行）

### 一个边界

`navigator.clipboard` 只在 **https 或 localhost** 可用。本地 5181 是 localhost，能用；如果哪天换到内网 IP 会静默失败——所以失败分支必须给提示，不能什么都不做。

## 步 3｜Markdown 渲染（40 min，需装依赖）

### 产品问题

**P3**：模型输出几乎必然是 Markdown（加粗、列表、代码块），现在按纯文本显示，用户看到的是 `**粗体**` 和 ``` 这种源码，可读性很差。

### 装依赖（这步需要你执行）

在本包 `package.json` 的 `devDependencies` 加（版本与 `workspace-kit` 一致）：

```json
"react-markdown": "^10.1.0",
"remark-gfm": "^4.0.1",
"rehype-highlight": "^7.0.2",
"highlight.js": "^11.11.1"
```

然后 `pnpm i`（会提示重装 node_modules，属预期）。

### 改哪里

`src/render/part-renderer.tsx` 的 `text` 分支 —— **不要回到 `main.tsx`**。

### 做法

```tsx
<Markdown remarkPlugins={[remarkGfm]} rehypePlugins={[rehypeHighlight]}>{part.content}</Markdown>
```

### 必须处理的坑（这是本步唯一有难度的地方）

**流式未闭合**：逐字输出时，` ``` ` 代码围栏、`**加粗**`、行内代码在**中途都是未闭合的**。直接扔给 Markdown 渲染器会出现：样式闪一下、代码块被当成普通段落、甚至整段被吞。

三个应对手段（按性价比排序）：

1. 不追求完美：让渲染器自己处理未闭合（`react-markdown` 多数情况能兜住），先看实际效果
2. 节流：内容变化太快时，用 `requestAnimationFrame` 或 50ms 节流合并渲染
3. 补齐：检测未闭合的围栏并临时闭合（`content.split('```').length % 2 === 0` 时补一个）

### 验收

- `**流式到达**` 显示为粗体
- ```ts 代码块高亮成代码块
- 流式过程中不闪、不整段消失

## 步 4｜附件最小版（可选，60+ min）

### 产品问题

**P4**：用户想"就这份文件提问"，但输入框只能打字，必须先把文件内容粘进来。

### 为什么放最后

它要动三层，且要 mock 配合：

| 层 | 要做的 |
|---|---|
| 提交协议 | `AgentSubmitPart` 已定义 `image` / `online_doc`，但 `AgentController.submit` 现在只接收文本 → 需要改成接收 parts |
| mock | `/chat` 的 `messages[].content_parts` 需要能接收并回显（现在完全忽略） |
| UI | 输入区加"附件 chip"（文件名 + 删除），发送时转成 part |

### 建议的最小范围

- 只支持**图片 URL**（不做上云、不做本地文件上传）
- chip 只显示文件名，点击无效
- 验收：发一条带图片的消息，`/chat` 请求体的 `content_parts` 里有 `image`，助手回复正常

### 明确不做

- 富文本编辑器（Slate）—— 编辑器内核不是 agent 议题
- 文件上云 / import-kit
- 拖拽上传的完整实现

## 已知取舍（写给自己，面试可讲）

| 不做 | 理由 |
|---|---|
| 富文本输入（Slate） | 编辑器内核不是 agent 议题，textarea + part 组装已能讲清"为什么用 parts 而不是字符串" |
| 文件上云 | 依赖 import-kit，成本高、面试价值低 |
| 长列表虚拟化 | 当前量级不是瓶颈；代价与解法记在 Day 2 的"逐帧不可变更新"里 |
| 工具卡交互（展开状态持久化） | 现在是组件局部 state，刷新即丢；要持久化得进 store，属于 Day 5 的范围 |
